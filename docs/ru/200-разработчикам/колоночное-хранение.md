# Колоночное хранение таблиц: план миграции

Статус: этап 1 в работе. Документ фиксирует решение до рефакторинга. Здесь перечислены риски и порядок миграции.

## Исходное состояние

`Table.data` — это `TableData::View` или `TableData::Owned`.

- `View` хранит плоский row-major `Vec<ValueId>` в `ValueStore`.
- `Owned` хранит плоский row-major `Vec<Value>` и ленивый `column_cache`.

Профиль табличного бенчмарка (1M строк) показывает, куда уходит время:

| Сценарий | DC/pandas | Главная статья расхода |
|---|---|---|
| newcol | ~180× | `append_column_owned` пересобирает всю таблицу. Каждая строка клонируется, в том числе каждая строка-`String`, а это `malloc`. На саму арифметику уходит ≈5%. |
| groupby, nulls | ~10× | Ячейка `Value` на каждое значение, ветвление по типу на каждую ячейку. |
| load, filter, join, sort | 3,5–5× | Построчный разбор CSV в `Value` и клонирование строк. |

Добавление колонки стоит O(rows × cols) и копирует всё, что уже есть в таблице. Это главный дефект.

## Целевая модель

1. **Колонка — неизменяемый разделяемый буфер.** После создания колонку никто не меняет. Изменение таблицы создаёт новую таблицу. Новая таблица ссылается на старые буферы и добавляет новые.
2. **`Rc`, а не `Arc`.** VM однопоточная: `Value` содержит `Rc<RefCell<…>>` и не является `Send`. `Arc` добавил бы атомарные инкременты на каждое разделение и не дал бы никакой гарантии, которой нет сейчас. Если таблицы когда-нибудь пойдут между потоками, менять придётся весь `Value`, а не только колонки.
3. **Копирование при записи не нужно.** Колонки неизменяемы, поэтому `Rc::make_mut` не понадобится. Мутирующие операции (`add_row`, `push`, присваивание ячейки) сначала переводят таблицу в `Owned` через `ensure_owned`. Если буфер разделён, он копируется, если уникален — забирается без копии.
4. **Мутация на месте через алиасы небезопасна.** Это ключевая причина нового варианта. После `m = n` обе переменные ссылаются на один heap-слот, поэтому `Rc::strong_count` таблицы не отличает уникальную таблицу от разделённой. Дописать колонку в `Vec` исходной таблицы нельзя: `m` увидела бы новую колонку. Новая таблица всегда отдельный объект. Общими у неё со старой могут быть только неизменяемые буферы.
5. **Типизированные колонки (позже).** Это `F64 { data: Rc<[f64]>, nulls: Option<Bitmap> }`, `I64 { … }` и `Str { offsets, bytes }`. Арифметика, null-заполнение и groupby тогда идут по срезам без `Value` на ячейку.

## Этап 1: колонка без копирования таблицы

Новый вариант:

```rust
TableData::Columnar {
    base: Rc<SharedRows>,              // row-major блок прежних колонок, неизменяемый
    extra: Vec<Rc<Vec<Value>>>,        // дописанные колонки, каждая длиной len
    headers: Vec<String>,              // base-заголовки + имена extra
    materialized: Rc<OnceCell<Vec<Value>>>, // ленивый row-major flat для построчных читателей
}
```

Поведение:

- **`table_add_column` для `Owned`.** Плоский буфер исходной таблицы переносится в `Rc<SharedRows>`, и исходная таблица становится `Columnar` без `extra`. Её содержимое и заголовки не меняются, меняется только представление. Новая таблица получает тот же `base` и одну колонку в `extra`. Стоимость O(1) по строкам.
- **`table_add_column` для `Columnar`.** Клонируются `Rc` базы и всех `extra`, затем добавляется новая колонка.
- **Колоночная арифметика** выдаёт `Columnar` с одной `extra`-колонкой. Поэтому `n!["c"] = n["a"] * n["b"]` кладёт результат в таблицу без копии: это `Rc::clone`. Операнды читаются срезом: base через шаг, `extra` подряд.
- **`column_view`** у `Columnar` отдаёт срез без материализации. `rows_ref`, `owned_flat` и прочие построчные читатели собирают row-major буфер один раз через `OnceCell`. Это та же работа, что раньше делал `append_column_owned`, только отложенная и, если таблицу читают только по колонкам, вовсе не нужная.
- **Мутаторы и `Owned`-only хелперы** вызывают `ensure_owned`. Он забирает материализованный буфер или собирает его, после чего логика работает как прежде.
- **`PartialEq`, `deep_copy`, `sqlite_export`, `abi_bridge`** работают через материализованный вид. Семантика не меняется.

### Почему не другие варианты

| Вариант | Причина отказа |
|---|---|
| Дописывать колонку в `Owned` на месте | Небезопасно при алиасах (пункт 4). |
| Добавить поле в `Owned` | Внешние `Owned { flat, .. }`-паттерны молча проигнорируют лишние колонки. Новый вариант заставляет компилятор показать каждое место. |
| Сразу полностью колоночный `TableData` | Около 30 `match` по `TableData` и порядка 80 вызовов построчных аксессоров. Большой одномоментный рефакторинг без промежуточных замеров. |

### Риски этапа 1

- **Внешние `match`.** Вне `table.rs` их 28: `table_ops`, `deep_copy`, `sqlite_export`, `abi_bridge`, `iterable`, `operations`, `natives/table`. Исчерпывающие `match` проверит компилятор. Ветки `if let Owned` сами по себе станут медленным путём, это корректно, но каждую надо проверить.
- **Смена представления исходной таблицы** при `add_column`. Таблица может быть одновременно заимствована: `RefCell` упадёт в рантайме. Нативный вызов не держит заимствований аргументов, но это нужно покрыть тестом. Сравнение `same_schema_binding` и `PartialEq` должно работать для смешанных пар `Owned`/`Columnar`.
- **Память.** Пока база разделена, а производная таблица материализована, в памяти лежат обе копии. Без этапа 1 копия была бы та же, но сразу.
- **Порядок колонок, дубликаты, длины.** Ошибки `already exists` и `length … does not match` сохраняются дословно.

## Последующие этапы

Каждый этап — отдельный коммит с замером до и после.

1. Добавление колонки без копирования. Арифметика по срезам.
2. Null-заполнение и `drop_nulls` по колонке без пересборки строк. Фильтр строит маску колонкой, а затем делает `gather`.
3. groupby по колонкам: хеш по ключевой колонке и аккумуляторы по срезам.
4. Типизированные колонки `F64`/`I64` с null-битмапом. Арифметика без `Value` на ячейку. Переполнение `I64` даёт откат на `f64`, как сейчас.
5. Типизированный CSV-парсер, сразу в колонки.
6. join и sort через перестановку индексов и `gather` колонок.

Совместимость: пользовательская семантика (порядок, null, типы `int`/`float`, ошибки) не меняется ни на одном этапе. Существующие тесты и `scripts/bench_tabular` — критерий приёмки.
